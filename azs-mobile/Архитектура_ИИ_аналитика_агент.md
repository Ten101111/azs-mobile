# Архитектура «ИИ-аналитика»: от «вопрос → SQL → ответ» к аналитическому агенту

Документ фиксирует, как контур ИИ устроен сейчас (срез на 22.09.2026), что в нём
меняется и как выглядит целевая архитектура AI Data Analyst. Реализация — в
`backend/ai/agent/` и `backend/ai/semantic.py`; всё, что работало до этого, продолжает
работать без изменений (режим FAST — это прежний контур целиком).

Базовые принципы, зафиксированные в БТ и приложении «Системные инструкции», сохраняются
без ослабления и имеют приоритет над любым пунктом технического задания на агента:

- права — в коде, поведение — в инструкции; область данных подставляет система;
- модель не имеет прямого доступа к витрине: каждый SQL проходит детерминированный
  валидатор (allowlist таблиц и колонок, только SELECT/WITH, LIMIT, таймаут);
- модель видит только каталог, а не information_schema; список таблиц не расширяется
  тем, что модель «нашла» в базе;
- каждое число в ответе — из витрины; если данных нет — говорится прямо: «За <период>
  данных в витрине нет. Доступен период с … по …»; показатель, которого нет в витрине,
  не досчитывается и не «предполагается»;
- чужие объекты в диалоге не называются (позиция и разрыв), терминология нормативная.

---

## 1. Как устроен контур сейчас

| Звено | Где | Как работает |
|---|---|---|
| Приём вопроса | `backend/ai/api.py` → `POST /api/ai/ask`, `/ask/stream` | Роль и привязка — из учётной записи (подмена только администратором). Диалоги и сообщения — `dialogs.py`, журнал — `journal.py`. Поток этапов — SSE-события `stage` → `answer`/`failed` |
| Область данных | `scope.py` + `backend/roles.py` | Роль → перечень КССС или «вся сеть». Не зависит от текста вопроса |
| Генерация SQL | `generator.py` | Ollama `/api/chat`, модель `AI_MODEL` (qwen3), temperature 0, `/no_think`. Из ответа вырезается один SELECT (`extract_sql`) |
| Системный промпт | `contract.py` | Описание витрины (`CATALOG.description` или встроенная схема стенда), 9 правил, глоссарий сокращений, 7 примеров «вопрос → SQL». Версия промпта — хеш текста |
| Описание схемы | `catalog.py`, `data/ai_catalog.dwh.json` | Каталог: таблицы, колонки, ключ объекта, диалект, схема, текст описания, примеры. Встроенный — стенд SQLite (`station_kpi_daily`, `stations`); файл — витрина ОХД (`dm.data_for_ai_analytic_part_1/2`) |
| Проверка SQL | `validator.py` | Разбор `sqlglot`: один SELECT, только таблицы и колонки каталога, запрещённые узлы и функции, подстановка области данных подзапросом вокруг каждой защищаемой таблицы, LIMIT 200 |
| Исполнение | `executor.py` | `sqlite` (стенд, read-only, progress-handler как таймаут) или `postgres` (READ ONLY, `statement_timeout`). Приведение типов на границе (`_normalize`) |
| Передача результата модели | `generator.narrate` + `contract.narration_prompt` | Второй вызов модели: первые 30 строк результата → 2–4 предложения без досчётов и советов |
| Финальный ответ | `pipeline.Answer` → `AskResponse` | `summary`, `columns/rows`, `notes`, времена этапов; SQL уходит только admin/subadmin |
| Фронтенд | `src/main.jsx` (`AnalyticsAiConsole`, `AiThinking`, `AiAnswerBody`) | Строка рассуждения из измеренных этапов (`draft/check/read/write`), геро-число или карточки фактов, таблица, свёртки «Откуда число» и «SQL-запрос», оценка звёздами |
| Инструменты (tools) | нет | Модель не вызывает инструментов: одна генерация SQL, одна попытка перегенерации по замечанию валидатора, одно пояснение |

Схема сегодня: `вопрос → generate → validate → run → narrate → ответ`, максимум два обращения
к модели и ровно один запрос к витрине. Контекст предыдущих вопросов модели не передаётся.

## 2. Что меняется и что остаётся

**Остаётся как есть (переиспользуется как инструменты агента):** `validator.py`,
`executor.py`, `scope.py`, `catalog.py`, `journal.py`, `dialogs.py`, `quality*.py`,
`generator.generate/narrate` (режим FAST и инструмент `draft_sql`), транспорт SSE,
хранение диалогов, правила приватности (диалог виден автору, SQL — admin/subadmin).

**Меняется:**

| Компонент | Изменение |
|---|---|
| `pipeline.ask` | Появляются параметры `depth` (`auto/fast/analyze/deep`) и `history` (прошлые ходы диалога автора). `fast` — прежний путь без единого изменения; остальное — `agent.run` |
| `pipeline.Answer` / `AskResponse` | Новые поля: `depth`, `taskType`, `analysis` (структурированный вывод), `charts`, `tables`, `steps` (измеренные шаги), `frame` (рамка контекста для следующих вопросов), `limitations` |
| `api.py` | `AskRequest.depth`; в контур передаются последние ходы **того же диалога того же автора**; код Python в шагах скрывается так же, как SQL |
| `journal.py` | Поздние колонки `depth`, `task_type`, `trace_json` (полная трасса шагов для разбора качества) |
| `catalog.py` | Читает секцию `semantic` каталога (метрики, измерения, группы сопоставимых) |
| Фронтенд | Рендер разделов ответа, графики (SVG, без библиотек), несколько таблиц, свёртка «Показать расчёты / SQL», этапы агента в строке рассуждения и в орбе, переключатель глубины |

## 3. Целевая архитектура

```
Пользователь ──► /api/ai/ask[/stream]  (роль, привязка, dialogId, depth=auto)
                       │
                       ▼
              pipeline.ask(question, scope, history, depth)
                       │
        ┌──────────────┴───────────────┐
        │ 1. memory.rewrite            │  ← последние ходы диалога (рамки: метрика,
        │    вопрос → самостоятельный  │    период, фильтры, объекты) — «А только
        │    вопрос + рамка            │    Москва?» становится полным вопросом
        └──────────────┬───────────────┘
                       ▼
        ┌──────────────────────────────┐
        │ 2. triage (одна модель-      │  тип задачи: lookup / compare / trend /
        │    вызов, JSON)              │  diagnose / anomaly / opportunity / whatif
        │    или эвристика для         │  глубина: fast / analyze / deep
        │    очевидных lookup          │  план: список проверок; метрики; период
        └──────┬───────────────┬───────┘
          fast │               │ analyze / deep
               ▼               ▼
   прежний контур        ┌────────────────────────────────────────┐
   generate→validate     │ 3. Цикл инструментов (модель-оркестратор)│
   →run→narrate          │   search_schema / get_metric_definition  │
                         │   get_dimension_values / get_data_range  │
                         │   run_sql  ─► validator ─► executor ─►   │
                         │             checks (пусто, NULL, дубли,  │
                         │             период, обрезка)             │
                         │   run_python (подпроцесс, лимиты)        │
                         │   create_chart (привязка к результатам)  │
                         │   finish(структурированный ответ)        │
                         │   бюджеты по глубине; каждый шаг — этап  │
                         └───────────────────┬────────────────────┘
                                             ▼
                         ┌────────────────────────────────────────┐
                         │ 4. finalize: ответ по структуре         │
                         │   Главный вывод / Что произошло / Почему│
                         │   / Где именно / Что можно сделать /    │
                         │   Ограничения данных                    │
                         │ 5. grounding: числа текста сверяются с  │
                         │   результатами; неподтверждённые фразы  │
                         │   убираются, факт фиксируется в трассе  │
                         └───────────────────┬────────────────────┘
                                             ▼
                journal (trace_json) · dialogs (answer_json + frame) · SSE → фронтенд
```

Ключевое отличие от жёстких сценариев: план и последовательность инструментов
выбирает модель; система ограничивает её **инструментами** (что можно сделать),
**валидатором** (что можно прочитать), **семантическим слоем** (что означают
показатели) и **бюджетом** (сколько шагов). Ни один класс вопросов не зашит как
фиксированная цепочка запросов.

## 5. Инструменты и интерфейсы

Все инструменты — чистые функции над `ToolContext` (область данных, каталог, семантика,
бюджет, рабочее пространство результатов). Модель получает их описание как JSON-схемы;
аргументы проверяются до вызова.

| Инструмент | Аргументы | Возвращает | Границы |
|---|---|---|---|
| `get_schema()` | — | таблицы каталога, назначение, ключ, гранулярность, диапазон дат | только каталог, не information_schema |
| `search_schema(query)` | текст | релевантные таблицы/колонки/метрики/измерения с описаниями; «не найдено» с ближайшими кандидатами | поиск по описаниям и синонимам семантического слоя |
| `get_column_metadata(table, column)` | имена | тип, описание, единица, примеры значений, доля NULL | примеры — через валидированный SELECT в области данных |
| `get_metric_definition(metric)` | ключ или синоним | формула (SQL-выражение для текущего диалекта), единица, направление, драйверы, оговорки | определения не генерируются моделью |
| `get_dimension_values(dimension, search?)` | измерение | допустимые значения (DISTINCT в области данных), для дат — min/max | LIMIT 100 |
| `get_data_range(table?)` | — | первая и последняя дата, число объектов | ответ на «есть ли данные за период» |
| `run_sql(sql, purpose)` | SELECT + короткая цель шага | `ResultSet` (id `rN`, колонки, строки ≤ лимита глубины, `warnings` из checks) | валидатор + область данных + LIMIT + таймаут; журнал |
| `draft_sql(question)` | вопрос на русском | SQL от прежнего генератора (`generator.generate`) — как черновик для `run_sql` | это прежний механизм text-to-SQL в роли инструмента |
| `run_python(code, inputs, purpose)` | код, список `rN` | stdout (≤ 20 КБ), `result` как новый `ResultSet` `pN` | подпроцесс, CPU 10 с, стена 20 с, белый список импортов (pandas, numpy, math, statistics), без сети и файлов |
| `create_chart(spec)` | `{type, title, source: rN/pN, x, series[], ...}` | нормализованный график `{type, title, x[], series[{name, values[]}]}` | данные берутся из результатов, не из текста модели |
| `finish(answer)` | структурированный ответ | завершает цикл | обязателен раздел `limitations`, если чего-то не было в данных |

**Формат графика для фронтенда**

```json
{ "type": "line | bar | stacked_bar | scatter | waterfall | kpi | table",
  "title": "Чеки по месяцам", "x": ["2025-10", "…"], "xTitle": "Месяц",
  "series": [{ "name": "Чеки, шт", "values": [123456, 0] }],
  "unit": "шт", "source": "r1" }
```

**Формат аналитического ответа** (`answer.analysis`)

```json
{ "headline": "1–2 предложения с главным результатом",
  "happened": ["ключевые цифры"], "why": ["факторы, подтверждённые данными"],
  "where": ["АЗС / регионы / категории, давшие эффект"],
  "actions": ["действие — объект — показатель — эффект — источник методики"],
  "limitations": ["чего в витрине нет; что не проверено"] }
```

## 6. Глубина анализа

| Режим | Когда | Бюджет |
|---|---|---|
| `fast` | lookup: одно число, одна таблица, простой топ | прежний контур: 1 SQL, 1 пояснение |
| `analyze` | сравнение, динамика, простая диагностика, топ по изменению | ≤ 5 SQL, ≤ 2 Python, ≤ 2 графика, ≤ 10 ходов модели, 1000 строк на запрос |
| `deep` | причины, аномалии, точки роста, what-if | ≤ 10 SQL, ≤ 4 Python, ≤ 3 графика, ≤ 18 ходов, 2000 строк |

В режиме `auto` глубину выбирает triage; очевидные lookup без контекста диалога
распознаются эвристикой без вызова модели, чтобы не удлинять простой ответ.
Пользователь может задать глубину явно (переключатель в настройках раздела).

## 7. Flow простого вопроса — «Сколько чеков было вчера?»

1. `memory.rewrite`: истории нет → вопрос без изменений.
2. Эвристика: «сколько … вчера» без слов сравнения/причин → `fast`, triage не вызывается.
3. Прежний контур: `generator.generate` → `SELECT ROUND(SUM(checks)) … WHERE metric_date = date('now','-1 day')`
   → `validate` (область данных, LIMIT) → `executor.run` → `narrate`.
4. Ответ: геро-число, пояснение, «Откуда число». Рамка: `{metric: checks, period: вчера}`.
   Этапы: составил → проверил → прочитал → сформулировал. Один вызов модели на SQL,
   один — на пояснение. Ничего нового пользователь не замечает.

## 8. Flow сложного вопроса — «Почему снизился трафик?»

1. `memory.rewrite`: если до этого спрашивали «чеки относительно прошлого месяца» —
   рамка даёт метрику `checks` и периоды; самостоятельный вопрос: «Почему количество
   чеков в сентябре 2026 снизилось относительно августа 2026».
2. `triage` → `{task: diagnose, depth: deep, plan: [динамика по дням/неделям,
   разложение по объектам, доля объектов с падением, драйверы: чеки НТУ/топливные,
   число работающих АЗС, сопоставимый период прошлого года], metrics: [checks, …]}`.
3. Цикл (пример реальной последовательности, число шагов выбирает модель):
   - `get_metric_definition("трафик")` → `SUM(checks)`, драйверы: `active_stations`,
     `checks_per_station`, `checks_ntu`, `checks_fuel`; оговорка стенда: «в стенде
     нет разбивки топливных/НТУ чеков по SKU и цене».
   - `get_data_range()` → есть ли полный сентябрь; иначе сравнение MTD с тем же
     отрезком августа.
   - `run_sql` №1 — чеки по неделям за 3 месяца (динамика);
   - `run_sql` №2 — чеки и число работающих АЗС за оба периода (общий эффект и эффект
     сети);
   - `run_sql` №3 — изменение по АЗС (доля объектов с падением, вклад топ-20);
   - `run_python` — разложение: эффект числа объектов × эффект на объект; концентрация
     падения (Парето); выбросы по группе сопоставимых (регион/формат) через медиану и
     межквартильный размах;
   - `run_sql` №4 — сопоставимый период прошлого года (сезонность);
   - `create_chart` — линия по неделям и waterfall драйверов;
   - `finish` — структурированный ответ.
4. `finalize` + `grounding`: каждое число сверено с `r1…r4`, `p1`. Раздел
   «Ограничения»: «цена, ассортимент и наличие товара в витрине стенда отсутствуют —
   влияние этих факторов не оценивалось»; «корреляция драйверов не доказывает причину».
5. Ответ: главный вывод, цифры, драйверы, где именно (свои объекты; чужие — позицией
   и разрывом), действия со ссылкой на методику, ограничения; графики; свёртка
   «Показать расчёты» с шагами (SQL и код — только admin/subadmin).

## 9. Семантический слой

Хранится рядом с каталогом (секция `semantic` в `data/ai_catalog*.json`; для стенда —
встроенные определения в `semantic.py`), не генерируется моделью. Единица описания:

```json
{ "key": "checks_per_100", "title": "Продажи НТУ на 100 клиентов",
  "aliases": ["на 100 клиентов", "на сто чеков", "проникновение"],
  "expr": "100.0 * SUM(sum_quant_ntu_retail) / NULLIF(SUM(cnt_cheq), 0)",
  "unit": "шт/100 чеков", "direction": "higher_better",
  "drivers": ["ntu_items", "traffic"], "notes": "количество товаров — по ретейлу" }
```

Помимо метрик: измерения (регион, ОНПО, формат, менеджеры — с указанием, как
получать допустимые значения), сущность «АЗС» (ключ, номер на вывеске, название),
группы сопоставимых АЗС для аномалий и точек роста (регион × формат × состав сервиса
на стенде; регион на витрине ОХД), правила периодов и соединений для диалекта.

## 10. Проверка результата и безопасность

- Каждый `run_sql` — через тот же валидатор, что и раньше (allowlist, SELECT-only,
  область данных, LIMIT, таймаут, журнал). Ничего не ослаблено; лимит строк для
  агента задаётся отдельно (`AI_AGENT_ROW_LIMIT`).
- `checks`: пустой результат (с подсказкой о доступном диапазоне дат), доля NULL по
  колонкам, полностью повторяющиеся строки, обрезка по лимиту, диапазон дат в
  результате. Предупреждения возвращаются модели вместе с данными и попадают в трассу.
- `run_python`: отдельный процесс, лимиты CPU/времени/вывода, импорт только из
  белого списка, нет доступа к файлам, сети, окружению и базе — данные передаются
  как уже прочитанные результаты.
- `grounding`: числа финального текста сверяются с данными и вычислениями; при
  расхождении — одна попытка исправления, затем неподтверждённые фразы убираются.
- Трасса шагов (`trace_json`) пишется в журнал для раздела «Качество ответов».

## 11. Что не делается намеренно

- Динамическое исследование information_schema/pg_catalog (п. 5 задания): противоречит
  принципу «модель видит только каталог». Инструменты схемы работают по каталогу и
  семантическому слою; расширение перечня таблиц — решение владельца данных и правка
  каталога, а не инициатива модели.
- Прогноз «на глаз»: только методика раздела 5 приложения (методы А и Б, порог 7 дней,
  диапазон вместо числа) — реализована примитивом `forecast_ab` в `analytics.py`.
- Уточняющие вопросы там, где ответ есть в данных: агент сначала смотрит диапазон
  дат и допустимые значения измерений и лишь потом (если неоднозначность реальная —
  например, объект назван числом, которое совпадает и с КССС, и с номером) показывает
  оба варианта, а не спрашивает.
