### Аутентификация и восстановление пароля
- Пароль хранится только как PBKDF2-SHA256-хеш — восстановить его нельзя, только сбросить.
- Сброс: экран входа → «Забыли пароль?» → код на корпоративную почту → код + новый пароль.
- Endpoints: `/api/auth/request-password-reset`, `/api/auth/reset-password` (все сессии сбрасываются).

### Аналитика использования (добавлено 19.08.2026)
- Таблицы в `data/auth.sqlite3`: `visits` (визиты: время входа/выхода, длительность, IP, устройство, браузер, PWA) и `usage_events` (просмотры экранов, открытия карточек АЗС, фильтры).
- Frontend шлет heartbeat раз в 60 с при видимой вкладке (`/api/metrics/beat`) и батчи событий (`/api/metrics/events`, sendBeacon при уходе со страницы).
- Визит закрывается после 30 мин неактивности (`ANALYTICS_VISIT_GAP_SECONDS`).
- Раздел «Админ» (плитка на главной, только для `ADMIN_EMAILS`): сводка, визиты по дням, популярность разделов, устройства, таблица пользователей, журнал входов. Endpoints: `/api/admin/users`, `/api/admin/activity?days=N`.

### Палитра приложения (PWA) — отдельно от документов

Значения выше относятся к документам и слайдам. В приложении с 21.09.2026
действует фирменный красный из спецификации облика ИИ:

```css
--red: #E31E24;        /* акцент: текст, границы, иконки */
--red-dark: #B8171C;
--red-fill: #E31E24;   /* заливка красных кнопок под белым текстом */
--red-fill-hover: #B8171C;
/* тёмная тема */
--red: #FF4A4F;        /* акцент осветляется ради читаемости */
--red-fill: #E31E24;   /* заливка тёмная: белое на #FF4A4F — 3,3:1, на #E31E24 — 4,69:1 */
```

Правило: `--red` — для того, что читается как цвет (текст, обводка, значок);
`--red-fill` — для того, на чём лежит белый текст. Менять местами нельзя,
иначе в тёмной теме кнопки теряют контраст.

PNG-иконки приложения (`public/icon-*.png`) несут настоящий логотип ЛУКОЙЛ
и к этой палитре не приводятся.

### Системные шкалы (с 21.09.2026)

Любая новая вёрстка берёт значения отсюда, а не подбирает на глаз:

```css
--s1…--s7      /* 4 / 8 / 12 / 16 / 24 / 32 / 48 — отступы кратны 4 */
--r-sm/md/lg   /* 10 / 14 / 20, плюс --r-full для пилюль */
--e1 / --e2    /* уровень 1 — поднятая подложка, 2 — плавающее */
--t-meta…--t-display  /* 12 / 13,5 / 16 / 20 / 44 */
```

Нейтральные — одна шкала тона 220° в обеих темах. Разделение линий:

- `--hairline` — разделители внутри блока;
- `--line` — то же, общее;
- `--line-mid` — декоративное: пунктиры, соединители, дорожки ползунка;
- `--line-strong` — **границы полей формы**, 3,29:1 к белому (WCAG 1.4.11).
  Не использовать как декоративную линию: она специально тёмная.

Правило поверхностей: контент лежит на фоне, разделяют его воздух и уровень.
Обводка остаётся только у того, что действительно поднято, — боковая панель,
поле ввода, модальное окно. `--icon-muted` — только для значков (порог 3:1);
текст красится `--muted` и темнее.

### Критический баг scale-to-fit (РЕШЁН)
Scale JS для слайдов должен использовать `document.body.offsetWidth - 32`, а НЕ `parentElement.offsetWidth`. Иначе скрытые слайды (display:none) получают width=0 и схлопываются. `scale()` вызывать ПОСЛЕ показа слайда в функции `go()`.

## Целевая архитектура (план развития v3.0)

### Источник данных
- **DWH PostgreSQL** — только чтение (read-only user)
- Обновляется **каждый час**
- Документация схемы DWH **отсутствует** — нужно создавать с нуля

### Целевой стек
```
React 19 PWA
    ↓
FastAPI + Uvicorn
    ↓
Redis (кеш сессий + результатов, TTL 30 мин)
    ↓
PostgreSQL App DB + PgBouncer (connection pooling)
    ↓
ETL (APScheduler, каждый час в :15)
    ↓
DWH PostgreSQL (read-only)
```

### Text-to-SQL архитектура (Этап 4)
```
Пользователь → текстовый запрос
    ↓
FastAPI /ai/query
    ↓
Ollama (localhost:11434) + Qwen2.5-Coder-14B-Instruct
(system-prompt = YAML-схема DWH из Этапа 1)
    ↓
SQL (только SELECT, проверка через sqlparse)
    ↓
PostgreSQL App DB → результат → пользователь
```

**ВАЖНО:** Никаких внешних API для ИИ. Только локальные модели через Ollama.
Требование безопасности компании — данные не должны покидать инфраструктуру.

## Дорожная карта (5 этапов)

### Этап 0: Инфраструктура (1–2 нед.)
- Docker Compose: Nginx + FastAPI + PostgreSQL + Redis + Ollama
- Миграция SQLite → PostgreSQL + PgBouncer
- Redis для сессий и кеша
- Read-only подключение к DWH

### Этап 1: Описание данных DWH (3–5 нед.) — КРИТИЧЕСКИЙ ФУНДАМЕНТ
1. Автовыгрузка структуры через `information_schema` → YAML-черновик
2. EDA по каждой таблице (COUNT, MAX/MIN, LIMIT 20)
3. Смысловое описание каждой таблицы и колонки вручную
4. ER-диаграмма связей (dbdiagram.io или draw.io)
5. «Контракт данных» для ETL (маппинг DWH → App)
6. Валидация с владельцем данных

Результат: YAML-файл 30–100 страниц. Используется ETL (Этап 2) и ИИ (Этап 4).

### Этап 2: ETL (2–3 нед.)
- APScheduler: инкрементальный ETL каждый час в :15
- Стратегия: `WHERE updated_at > последний_запуск`
- Полная перезагрузка ночью (раз в сутки)
- Materialized views для дашбордов (REFRESH CONCURRENTLY)
- Таблица `etl_log`, эндпоинт `/api/data-health`
- Плашка «Данные актуальны на: X минут назад»

### Этап 3: RBAC + Алерты + Пилот (3–4 нед.)
- Admin-панель: создание/редактирование/блокировка пользователей
- JWT с ролями + PostgreSQL RLS
- Push-алерты (Web Push API + VAPID + SMTP)
- Экспорт Excel (openpyxl) и PDF (WeasyPrint)
- Запуск пилота (10–15 человек), сбор обратной связи

### Этап 4: Локальный ИИ Text-to-SQL (6–8 нед.)
- Ollama + Qwen2.5-Coder-14B-Instruct Q4 (10–12GB VRAM)
- YAML-схема из Этапа 1 → system-prompt
- POST /ai/query → LLM → SQL → проверка → результат
- Redis Queue для 1 000 пользователей (очередь)
- Чат-интерфейс с кнопками «👍 Верно» / «👎 Неверно»

## Аналитический агент (с 22.09.2026)

Контур «вопрос → SQL → ответ» стал одним из режимов (FAST). Поверх него —
агент: разбор задачи, план, серия инструментов, структурированный ответ.
Полное описание — «Архитектура_ИИ_аналитика_агент.md»; здесь то, что нужно
помнить при правках.

**Где что лежит**

- `backend/ai/pipeline.py` — точка входа `ask(question, role, binding, actor, model, on_stage, depth, history)`.
  `depth`: `auto | fast | analyze | deep`. `fast` без истории — прежний путь без единого
  изменения (`_ask_fast`). Иначе разбор задачи (`agent.loop.triage`): эвристика
  `memory.looks_like_lookup` отправляет очевидный факт-вопрос на быстрый путь без
  обращения к модели, остальное — одна JSON-подсказка модели. `MODEL_FACTORY` —
  точка подмены модели в тестах и сценарном прогоне.
- `backend/ai/semantic.py` — семантический слой: показатели (ключ, формула, единица,
  направление, драйверы), измерения, сущность «АЗС», правила периодов, группы
  сопоставимых и список **того, чего в витрине нет**. Два встроенных профиля — стенд
  SQLite и витрина ОХД; секция `semantic` файла каталога дополняет и переопределяет
  формулы без правки кода. Формулы модель берёт отсюда, а не придумывает.
- `backend/ai/agent/` — `loop.py` (оркестратор), `tools.py` (реестр и проверка аргументов),
  `schema_tools.py` (схема по каталогу, не по information_schema), `sql_tool.py` (run_sql
  через прежний валидатор и исполнитель + `checks.py`), `sandbox.py` (run_python в
  подпроцессе, белый список импортов, без окружения и файлов) + `analytics.py`
  (примитивы: тренд, выбросы, разложение LMDI, парето, what-if, прогноз А/Б по методике),
  `charts.py` (create_chart: значения берутся из результатов, не из текста модели),
  `memory.py` (рамки диалога, эвристики), `grounding.py` (сверка чисел ответа с данными),
  `prompts.py`, `llm.py` (Ollama с tool calls / JSON, `ScriptedModel`), `state.py`.
- `backend/ai/agent_demo.py` — прогон шести вопросов владельца: `--scripted` без модели
  (проверяет контур), без флага — живая Ollama. Запуск через `scripts/python.sh`.
- `src/aiAnalysis.jsx` — ответ агента: структура, графики на SVG (line, bar,
  stacked_bar, scatter, waterfall, kpi, table), таблицы, «Показать расчёты».
  `main.jsx` подключает его в `AiAnswerBody` (когда у ответа есть `analysis`) и в
  `aiStages` (этапы из `answer.steps`). Переключатель глубины — в настройках раздела.

**Правила, которые нельзя ослаблять**

1. Каждый SQL агента идёт через тот же `validator.validate` с областью данных и LIMIT;
   у агента отдельный лимит строк (`AI_AGENT_ROWS`, `AI_AGENT_DEEP_ROWS`), не снимать.
2. Модель видит только каталог. Инструменты схемы читают каталог и семантический слой;
   `information_schema` не используется намеренно (п. 5 задания отклонён владельцем в
   пользу принципа allowlist). Новая таблица появляется правкой каталога, не инициативой модели.
3. Числа в тексте ответа сверяются с результатами (`grounding`): одна попытка исправления,
   затем неподтверждённые фразы убираются, факт пишется в трассу. Пороги из SQL и кода
   считаются законными свидетельствами.
4. Пустой результат — не ноль: и быстрый путь (`_no_data_note`), и агент (`checks`) говорят
   «данных нет» с доступным диапазоном дат. Показатель из списка `absent` не досчитывается —
   попадает в «Ограничения данных».
5. Python-код и SQL шагов уходят на клиент только admin/subadmin (`_strip_code` в api);
   текст шагов (purpose) — всем. История диалога в разбор берётся только из диалога автора.
6. Песочница — защита от ошибок модели, не граница безопасности: подпроцесс, лимиты CPU/
   времени/вывода, белый список импортов, без переменных окружения. Не давать ей сеть и базу.
7. Бюджеты глубины (`state.Budget`): analyze — 5 SQL / 2 Python / 2 графика / 10 ходов;
   deep — 10 / 4 / 3 / 18; общий предел `AI_AGENT_MAX_SECONDS` (240 с). Ollama:
   `AI_AGENT_NUM_CTX` (16384) — меньше нельзя, серия результатов не поместится.

**Формат ответа агента (API)**: к прежним полям добавлены `depth`, `taskType`,
`analysis {headline, happened[], why[], where[], actions[], limitations[]}`, `charts[]`
(`{id, type, title, x[], series[{name, values[]}], unit, source}`), `tables[]`, `steps[]`,
`frame` (рамка для следующего вопроса), `plan`, `grounding`, `planMs`. Всё это лежит в
`answer_json` сообщения диалога и в `trace_json` журнала.

**Проверено**: 106 тестов (`backend/tests`, из них 35 новых в `test_ai_agent.py`);
сценарный прогон шести вопросов на полном стенде — 6 из 6, числа подтверждены;
стенд интерфейса — десктоп и телефон, без ошибок и горизонтальной прокрутки.
**Не проверено**: живая модель qwen3 через Ollama из среды разработки недоступна —
первый живой прогон делает владелец (`scripts/python.sh -m backend.ai.agent_demo`).
Ожидаемые слабые места 8B-модели: JSON разбора задачи (есть запасной план), выбор
инструментов (есть подталкивание и принудительный финал), длина контекста.

## Раздел «ИИ-аналитик» в приложении

Собран 21.09.2026 по прототипу, согласованному с владельцем.

- **Фронтенд:** `src/main.jsx`, блок от `function AiMark` до конца
  `AnalyticsAiConsole`; стили — блок «Раздел «ИИ-аналитик»» в `src/styles.css`.
  Боковая панель с историей, лента колонкой по центру (760px), строка
  рассуждения, свёрнутые блоки, окно оценки звёздами, выдвижная история
  на телефоне.
- **Бэкенд:** `backend/ai/dialogs.py` — диалоги, сообщения и оценки в той же
  базе, что и журнал обращений (`JOURNAL_DB`), связь через `journal_id`.
  Маршруты — в `backend/ai/api.py`.
- **Три правила, которые нельзя ослаблять** (проверяются тестами
  `backend/tests/test_ai_dialogs.py` и `test_ai_api.py`):
  1. Диалог виден только своему автору, включая администратора. Администратор
     работает со сводкой оценок (`GET /api/ai/quality`), а не с перепиской.
  2. Оценка до трёх звёзд включительно требует комментария — на сервере,
     а не только в интерфейсе.
  3. SQL уходит на клиент только администратору и субадминистратору
     (`_may_see_sql`). Прятать его вёрсткой недостаточно: он был бы виден
     в трафике.
- **Этапы в строке рассуждения строятся только из измеренных величин**
  (`model_ms`, `narrate_ms`, `sql_ms`, `attempts`, `row_count`). Не добавлять
  этап, время которого никто не засекал.
- **Движение.** Ровно три анимации на framer-motion: вход сообщения (8 px +
  прозрачность, 220 мс), пружинное раскрытие свёрнутого блока (`AiReveal`),
  поочерёдное проявление этапов (40 мс на этап). Больше в ленту не добавлять.
  Въезжает только то, что пришло в этом сеансе (`freshIds`), иначе открытие
  старого диалога выглядит как поток новых сообщений. Всё уважает
  `useReducedMotion`.
- **Поток этапов.** `POST /api/ai/ask/stream` отдаёт события `stage`, затем
  `answer` либо `failed`. Конвейер сообщает об этапах через `on_stage`;
  слушатель не должен ронять ответ, поэтому исключение в нём гасится.
  Клиент читает обычным `fetch` (не `EventSource`: тот умеет только GET,
  а вопрос в адресной строке попадёт в логи прокси) и при неудаче молча
  повторяет через `/ask`.
  **Не включать gzip на этом пути** — компрессор копит байты, и этапы
  приедут пачкой в конце. За это отвечает `StreamFriendlyGZip` в
  `backend/main.py`; TestClient буферизует тело, поэтому разброс во времени
  проверяется только прогоном через настоящий сервер.
- **Раскладка раздела.** Высота считается раскладкой, а не подобранным
  числом: `.app-shell.ai-mode .workspace` — колонка, `.view-stage` и
  `.analytics-pane` сжимаются, лента листается внутри себя. Не возвращать
  `calc(100dvh - N)`: при другой высоте шапки поле вопроса уезжает за край.
  Нижнюю кромку можно тянуть (`--ai-extra`, запоминается в localStorage),
  на телефоне кромки нет.
- **Подсказки.** Нажатие кладёт вопрос в поле ввода, а не отправляет:
  период или объекты почти всегда хочется поправить. Три штуки, не больше:
  четвёртая не помещается.
- **Телефон.** Поле ввода — 85 px: текст и кнопка отправки в одну строку,
  подпись-подсказка под полем скрыта. Всё, что отнимаешь у поля, достаётся
  ленте, а она на телефоне и так короткая. По всей цепочке
  `.ai-shell → … → .ai-table-card` стоит `min-width: 0`: у flex-элемента
  по умолчанию `min-width: auto`, и одна широкая таблица внутри ответа
  растягивала весь раздел за правый край экрана. Не убирать.
- **Кнопка истории диалогов живёт в шапке приложения**, а не в заголовке
  раздела: на телефоне это единственное место, где она не отнимает высоту
  у ленты. Состояние панели (`aiDrawer`) поэтому поднято в `App`, а консоль
  принимает его пропсами `drawer` / `onDrawer`.

- **Пустой экран.** Там стоит крупный орб (`AiOrb`), размер — переменная
  `--ai-orb-size` на `.ai-welcome` (240 px десктоп / 144 телефон, коридоры по
  высоте окна; ниже 760 px десктоп опускается до 168–190 px — иначе поле
  вопроса уезжает за край, а спрятанный ввод хуже уменьшенного орба). Ярлык
  на кнопке-подсказке короткий, модели уходит полная формулировка с периодом
  (`AI_EXAMPLES` — пары `hint`/`ask`). Размеры задаются переменными, а не
  width/height в разметке: инлайновый стиль перебивает правило. У блока
  `justify-content: safe center` — обычное `center` при нехватке места
  срезает **верх**.

### Крупный орб — порт «Recursive Erosion»

`src/orb/`: `orbEngine.js` (движок без зависимостей), `AiOrb.jsx`
(React-обёртка на Framer Motion), `demo.html`, `README.md`. Решение владельца
от 22.09.2026: орб — **точь-в-точь** «Recursive Erosion» (Meng To, ThreeUI,
MIT; 21st.dev/@mengto), только в корпоративных цветах. Предыдущая SDF-версия
лежит рядом как `*.sdf.legacy.js` — не подключена, хранится для истории.

- **Что это.** Не Three.js и не SDF, а частицы на WebGL1: 2500 точек на сфере
  Фибоначчи, симплекс-шум мнёт сферу, второй шум с порогом выедает дыры
  (эрозия), семь «червей» ползут по большим кругам и подсвечивают точки,
  третий проход рисует их хвосты жемчужинами со свечением, поверх — зерно
  вторым холстом. Исходник взят из registry 21st.dev и портирован дословно:
  геометрия, шум, черви, проходы, константы. **Не «улучшать» эти числа** —
  владелец просил ровно референс.
- **Что изменено, в шейдере помечено `LUKOIL`:** палитра (оранжевая лестница
  cDim→cMid→cHot стала красной), убран бейдж-подпись, пять констант стали
  пружинными параметрами состояний — порог эрозии `thr`, амплитуда смятия
  `morph`, сила трасс `worms`, скорость петли `speed`, яркость `light`; плюс
  `mute` для отказа и ошибки (уход в металл #8A8D92).
- **Фон прозрачный везде** (решение владельца). Красный по светимости вдвое
  темнее оранжевого, поэтому у движка `mode: dark | light | auto`, как у
  оригинального компонента: на тёмном ступени палитры подняты (иначе решётка
  в покое исчезает), на светлом — опущены, «горячий» край упирается в чистый
  #E31E24, зерно не рисуется. `AiOrb` передаёт `mode="auto"`.
- **Размер точек.** Оригинал рассчитан на мастер 1080 px; на 120–240 px точки
  вырождались в пыль. Ниже 400 px они растут в полтора раза с полом 1,5 px.
- **Reduced motion** — как в оригинале: петля стоит на кадре 1,2 с, смена
  состояния перерисовывает кадр один раз.
- **Состояния** — цели параметров, к которым каждый идёт своей пружиной;
  переходы перекрываются сами. Шесть из брифа (idle, listening, searching,
  analyzing, forming, ready) плюс refused и error для исходов приложения.
  `orbStateFromPipeline`: набор текста → listening, draft и check → searching,
  read → analyzing, write → forming, исход → ready / refused / error.

### Как орб вшит в ленту

- **Пустой экран** — `idle`; `listening`, пока курсор в поле или набран текст;
  клик по орбу ставит курсор в поле. Размер — `--ai-orb-size` на `.ai-welcome`.
- **Блок ожидания** (`AiThinking pending`) — орб над строкой этапов.
- **Момент «готово» показывает `AiSettleOrb`** в пришедшем ответе: блок
  ожидания уходит из дерева в тот же кадр, в который приходит ответ, сказать
  ему «готово» некому. Орб передачи монтируется на том же месте (вопрос и
  ответ свёрстаны одинаково), стартует с параметров «формирую»
  (`initialState`), без появления (`appear={false}`), переходит в исход
  и через 1,4 с сворачивается. Ответ не задерживается ни на кадр. Колбэк
  `onSettled` — через ref: родитель перерисовывается на каждое нажатие
  клавиши, и таймер иначе сбрасывался бы.
- В ленте никогда не живёт больше одного WebGL-холста; после ответа крупных
  холстов в DOM нет. Не ставить `AiOrb` в повторяющиеся элементы.
- Без WebGL `AiOrb` рендерит `fallback` — в обоих местах туда передан `AiMark`.

### Тема

Приложение атрибут `data-theme` не ставит — тема только системная. Правила
для тёмной темы пишутся в `@media (prefers-color-scheme: dark)`; селектор
`:root:not([data-theme="light"])` применялся бы всегда (так и было
21–22.09.2026, исправлено).

### Что осталось от SDF-версии и зачем это помнить

Уроки, которые пригодятся, если SVG-орб (`variant="orb"`) снова понадобится:
в SVG нет `<defs>` и фильтров (им нужны id, а знак повторяется); свет —
отдельный слой `::before`, а не фон корпуса; яркость мелкого знака — множитель
`--orb-light`, а не перезапись `--orb-core-op`; толщина контура `--orb-stroke`
в единицах viewBox и на мелких размерах её надо поднимать; «сбившийся слой»
в ошибке — только дуга, повёрнутый круг неотличим от неповёрнутого.

## РУ, ТМ, статус и тип АЗС на витрине ОХД (с 23.09.2026)

В витринах `dm.data_for_ai_analytic_part_1/2` нет привязки объектов к людям, поэтому
вопрос «какой ВД НТУ у Ивановой» раньше давал пустые суммы. Источник — справочники
схемы `bds` (запрос владельца от 23.09.2026):

| Таблица | Что видит модель | Ключ | Как соединять |
|---|---|---|---|
| `bds.l_azs_rm_dt_vers` | `rm_fio` — РУ | `ksss_code` | `rm.ksss_code = f.ksss_azs_code AND f.account_date >= rm.dt_vers_start AND f.account_date <= rm.dt_vers_end` |
| `bds.l_azs_tm_dt_vers` | `tm_fio` — ТМ | `ksss_code` | то же с `tm` |
| `bds.s_azs_ksss` | `status_azs_name`, `type_azs_name` (наличие кафе и магазина — «формат») | `ksss_azs_code` | `k.ksss_azs_code = f.ksss_azs_code`, значения текущие, не на дату |

**Где что лежит**

- `backend/ai/build_dwh_catalog.py` — справочники описаны вручную (`REFERENCES`): только
  эти четыре поля и ключи, правило соединения по периодам (`people_note`), правило поиска
  по фамилии и три примера (фамилии вымышленные). Каталог пересобирается командой
  `scripts/python.sh backend/ai/build_dwh_catalog.py`; `data/ai_catalog.dwh.json` в git не входит.
- `backend/ai/check_dwh_people.py` — проверка справочников на машине с доступом к ОХД:
  типы ключей, пустой конец действующих периодов, пересечения периодов (задвоение сумм),
  покрытие дней последнего месяца, одна ли строка на объект в `s_azs_ksss`, точные
  значения статуса и типа. Печатает только агрегаты, ФИО не выводит. Пишет
  `DWH_outputs/bds_values.json`; сборщик каталога берёт из него значения статуса и типа и,
  если конец периода пустой, переключает соединение на `COALESCE(dt_vers_end, DATE '9999-12-31')`.
- Каталог (`catalog.py`): у таблицы может быть своя схема (`table_schemas`), свой ключ
  области данных (`scope_columns`) и проекция (`projected_tables`).
- Валидатор: таблица из своей схемы без префикса получает его автоматически; схема
  чужая — отказ; справочник всегда подменяется подзапросом с явным списком столбцов
  каталога (для любой роли), для ограниченной роли — ещё и с фильтром по своему ключу
  (`ksss_code IN (…)`). Поэтому `SELECT *` и обращения из CTE не достают из `bds` ничего,
  кроме описанных полей.
- Семантика ОХД: измерения `regional_manager`, `territory_manager`, `station_status`,
  `station_type`, соединения в `entity`, правила про периоды и фамилии; из «чего нет»
  убраны РУ/ТМ и состав сервиса.
- Контракт FAST: на витрине ОХД действуют свои правила (`contract.DWH_RULES`) —
  прежние правила стенда запрещали любые таблицы, кроме двух таблиц SQLite.
- `backend/ai/people.py` — кто назван в вопросе, решает код, а не модель. До обращения к
  модели резолвер берёт всех РУ и ТМ из справочников в пределах области данных
  пользователя (через валидатор; кэш на `AI_PEOPLE_TTL`, 30 мин), находит фамилии в любом
  падеже и применяет правила владельца от 23.09.2026: (1) РУ и ТМ между собой не
  сравнивают — все названные считаются на одном уровне; (2) фамилия есть и среди РУ, и
  среди ТМ — речь о РУ; (3) один только РУ, другой только ТМ — каждый отдельно, без
  сравнения. Модели уходит блок «ЛЮДИ В ВОПРОСЕ» с точными ФИО и фильтром
  `rm_fio IN (…)` / `tm_fio IN (…)` (в FAST — через `generator.generate(context=…)`, в
  агенте — через `hits["people"]`), пользователю — пометка в ответе, кто есть кто. На стенде
  источник — поля `regional_manager` / `territory_manager` таблицы `stations`. Те же правила
  записаны в справочник сокращений (`contract.GLOSSARY`), в описание каталога ОХД и в
  семантику — на случай, когда резолвер фамилию не нашёл.
- Проекция действует и для витрин `dm`: из таблицы выходят только столбцы каталога,
  нужные запросу (`validator._projection`), поэтому `rating` и `dt_ins` недоступны даже
  через `SELECT *` или CTE.

**Правила, которые нельзя ослаблять**

1. Новые поля справочников — только правкой `REFERENCES` в сборщике, по решению владельца.
   Модель не должна видеть ни телефонов, ни других столбцов этих таблиц.
2. Итог по руководителю считается по дням закрепления: объект, сменивший ТМ в середине
   месяца, делится между двумя ТМ. Если проверка покажет пересечения периодов — сначала
   правило выбора периода, потом ответы по людям.
3. Фамилия ищется в обоих справочниках (UNION ALL `rm_fio` и `tm_fio`) по основе без
   окончания через `ILIKE`; в ответе — полное ФИО, роль и число АЗС.

## Область данных ИИ на витрине ОХД (с 23.09.2026)

Решение владельца: ИИ живёт в ДВХ и всё считает в нём. При `AI_DB_BACKEND=postgres`
список объектов пользователя вычисляется запросом к ОХД, а не по `stations.json`
(`backend/ai/dwh_scope.py`, вызывается из `scope.build`; этим же путём идут плитки сводки):

| Роль | Откуда объекты |
|---|---|
| РУ / ТМ | `bds.l_azs_rm_dt_vers` / `bds.l_azs_tm_dt_vers`: закреплённые за ФИО из привязки на сегодня |
| АУП общества | `dm.data_for_ai_analytic_part_1`: объекты с этим `npo` за `AI_SCOPE_NPO_DAYS` дней (60) |
| Управляющий, агент | КССС из привязки как есть |
| Вся сеть | без запросов |

- Запросы системные, значение привязки экранируется; результат кэшируется на `AI_SCOPE_TTL` (30 мин).
- Витрина не ответила — область пустая с причиной в подписи, не «вся сеть»; ошибка не кэшируется.
- Режим «от имени» и самопроверка изоляции (`selfcheck`) берут РУ/ТМ/ОНПО тоже из ОХД.
- Стенд SQLite не изменился: там область по справочнику приложения (`roles.resolve`).
- Аварийный выключатель: `AI_SCOPE_SOURCE=reference` возвращает прежний способ.
- В каталог добавлен пример «Кто РУ и ТМ у АЗС 5044» (РУ и ТМ на сегодня, объект по КССС или номеру).

**Известное расхождение (З-29, бэклог).** Экраны и карточка АЗС по-прежнему работают по
`stations.json`: один и тот же пользователь может видеть на экране и в ИИ разный набор

пустая с пометкой «в ОХД нет объектов по этой привязке»). На время пилота допустимо.

## Исполнитель SQL: стенд и витрина

`AI_DB_BACKEND=sqlite` — демонстрационный стенд, `postgres` — витрина в ОХД.
Переключение меняет не только источник, но и **типы значений**, и это
единственное, что стенд проверить не может.

- **Всё, что приходит из драйвера, проходит через `_normalize`** в
  `backend/ai/executor.py`. psycopg2 отдаёт NUMERIC как `Decimal`, даты —
  как `date`/`datetime`, плюс UUID и `memoryview`; дальше строки уходят
  в `json.dumps` — в поток ответа, в журнал, в диалог и в выгрузку. Без
  приведения первый же вопрос про выручку падает с «Object of type Decimal
  is not JSON serializable». Приводим на границе исполнителя, а не
  в потребителях: потребителей четыре, и один обязательно забудут.
- **Целевые типы — те же, что даёт SQLite**, чтобы один вопрос давал
  одинаковый ответ на стенде и на витрине: целочисленный `Decimal` → `int`,
  дробный → `float`, дата → строка ISO.
- **NaN и Infinity превращаются в `null`.** `json.dumps` пишет их голыми
  литералами `NaN`/`Infinity` — это невалидный JSON, и `JSON.parse`
  в браузере падает на всём ответе. В Postgres NaN даёт и float8, и
  NUMERIC (например, деление на ноль в плане).
- **Целое за 2^53 уходит строкой.** В JavaScript такое число молча
  округлится, и человек увидит неверную цифру, не поняв этого.
- **Проверки стенда не ловят ошибки типов витрины.** Эталонный набор
  и `selfcheck` гоняются по SQLite, где `Decimal` не существует. Всё, что
  касается типов, закрывается тестами `backend/tests/test_ai_executor_types.py`
  на подменённом исполнителе, а не прогоном по стенду.

## Python окружения

Системный `python3` на машине владельца — Homebrew 3.14, там зависимостей
бэкенда нет (под 3.14 нет сборок `pandas` и `psycopg2`). Рабочее окружение —
`.venv` на 3.12. Всё, что запускает бэкенд, ходит через `scripts/python.sh`;
голый `python3` допустим только у `npm start` (`scripts/run_app.py`), который
это окружение и собирает. Новый скрипт с `python3 -m uvicorn` внутри — это
готовая ошибка «No module named uvicorn».

## Администрирование

Три вкладки (`ADMIN_TABS`): пользовательская аналитика, перечень
пользователей, качество ответов ИИ. Последняя появляется только при
включённом контуре ИИ; если контур выключили, а вкладка выбрана, она
переключается на аналитику сама. Переключатель периода показывается
только на вкладке аналитики — у качества свой.

## Раздел «Качество ответов»

Панель в админке (`AiQualityPanel`), данные — `backend/ai/quality.py`.

- Отказ (граница области данных сработала) и техническая ошибка (сломался
  контур) считаются **раздельно**. Смешивать нельзя: лечатся по-разному.
- Дата первичной реакции ставится один раз, при первом переводе из «Новой».
  Иначе срок можно «обновить» повторным нажатием, и просроченных не станет.
- Версия системной инструкции считается из её текста
  (`contract.prompt_version()`), а не ведётся руками, и пишется в журнал.
  Без этого срез «до и после смены версии» (БТ-КК7) не строится.
- Переписки в разделе и в выгрузке нет — только метаданные, оценка,
  комментарий и текст запроса к витрине (модель приватности ИБ-4, БТ-КК8).
  Выгрузка не должна давать больше, чем экран.
- Надпись про БТ-КК10 в интерфейсе обязательна: как только оценка попадёт
  в разговор о работе человека, низкие оценки исчезнут, и продукт перестанет
  получать сигнал о том, где врёт. С 21.09.2026 она не отдельный блок,
  а последняя фраза подписи под лентой оценок — владелец просил убрать
  блок. Совсем убирать фразу нельзя без правки самого БТ-КК10.

  классификатор вопросов для фильтра по классу (БТ-КК4).
