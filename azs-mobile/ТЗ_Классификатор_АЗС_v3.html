Описание данных DWH — это не просто документация. Это одновременно: (1) техническое задание для ETL, (2) system-prompt для локального ИИ, (3) общий язык с DWH-командой. Один раз сделать хорошо — экономит недели в будущем.

Пошаговый процесс описания:

1
Автоматически выгрузить структуру всех таблиц
Python-скрипт обходит information_schema и выгружает: список всех таблиц и схем, все колонки с типами данных, внешние ключи, существующие комментарии (если есть). Результат — базовый YAML с «скелетом» без смысла.
⏱ 1–2 дня
2
Разведочный анализ данных (EDA) по каждой таблице
Для каждой таблицы выполнить: COUNT(*), MAX/MIN по дате, образцы данных (LIMIT 20), кардинальность ключевых полей. Это позволяет понять что хранится в таблице даже без документации — по реальным данным.
⏱ 3–5 дней (на 50–100 таблиц)
3
Смысловое описание каждой таблицы (самое трудоёмкое)
Для каждой нужной таблицы заполнить: что это за сущность, какой бизнес-процесс отражает, что означает каждая колонка, единицы измерения, список возможных значений для статусов и кодов. Формат — YAML, по одному файлу на таблицу.
⏱ 1–2 недели (основная работа)
4
Построить ER-диаграмму связей между ключевыми сущностями
Нарисовать связи: АЗС-справочник → KPI-метрики → проверки → персонал. Определить ключи: azs_id, region_code, npo_code. Инструмент: dbdiagram.io (бесплатно) или draw.io.
⏱ 2–3 дня
5
Зафиксировать «контракт данных» для ETL
Таблица маппинга: поле в DWH → поле в приложении → трансформация (если нужна). Это граница ответственности: если DWH-команда переименует колонку — вы сразу знаете что сломается.
⏱ 1–2 дня
6
Валидация с владельцем данных
Показать описание аналитику или DWH-инженеру компании — убедиться, что вы правильно поняли смысл полей. Особенно важно для финансовых метрик (выручка gross/net, с НДС/без) и статусных кодов АЗС.
⏱ 1–2 встречи
# Скрипт автовыгрузки структуры DWH → базовый YAML import psycopg2, yaml conn = psycopg2.connect("host=dwh-host dbname=dwh user=ro_user password=...") cur = conn.cursor() cur.execute(""" SELECT t.table_schema, t.table_name, c.column_name, c.data_type, c.is_nullable, col_description( (t.table_schema||'.'||t.table_name)::regclass::oid, c.ordinal_position ) AS comment FROM information_schema.tables t JOIN information_schema.columns c USING (table_schema, table_name) WHERE t.table_schema NOT IN ('information_schema','pg_catalog','pg_toast') ORDER BY t.table_schema, t.table_name, c.ordinal_position """) schema = {} for schema_n, table_n, col, dtype, nullable, comment in cur.fetchall(): key = f"{schema_n}.{table_n}" if key not in schema: schema[key] = {"description": "TODO", "columns": {}} schema[key]["columns"][col] = { "type": dtype, "nullable": nullable == "YES", "description": comment or "TODO" } with open("dwh_schema_draft.yaml", "w", encoding="utf-8") as f: yaml.dump(schema, f, allow_unicode=True, default_flow_style=False)

После завершения описания схемы
DWH обновляется каждый час. ETL-сервис запускается через 15 минут после обновления DWH (например, в :15 каждого часа) — данные в приложении отстают не более чем на 1 час 15 минут. Это отличная свежесть для оперативного управления.

Инкрементальный ETL: только изменения, не весь объём
Стратегия: каждый час забирать только строки, где updated_at > время последнего запуска. Ночная полная перезагрузка раз в сутки. Это намного быстрее и не нагружает DWH.

Что такое «управление пользователями» — простое объяснение

Представьте: завтра в компанию выходит новый менеджер по АЗС. Кто создаёт ему аккаунт в приложении? Кто назначает ему роль «Региональный менеджер ЦНП»? Когда он уволится — кто заблокирует его доступ? Это и есть «управление пользователями».

Вариант А — Рекомендую на старте
Ручная admin-панель
Администратор (вы или назначенный IT-сотрудник) создаёт аккаунты вручную
Форма: Email @lukoil.com → выбрать роль → выбрать НПО/регион
Деактивация: кнопка «Заблокировать» в списке пользователей
Журнал: кто и когда создал/изменил аккаунт
Подходит для пилота 10–15 человек и роста до ~200 человек
Вариант Б — Для масштаба 1 000 человек
Интеграция с Active Directory (AD)
Active Directory — это корпоративная система IT, где уже есть все сотрудники ЛУКОЙЛ
Новый сотрудник появился в AD → автоматически создаётся аккаунт в приложении
Уволился → IT отключил в AD → доступ в приложении тоже закрылся
Роль назначается по группе в AD (все из «АЗС_Директора» = роль Директора)
Нужно уточнить у IT: есть ли в компании AD и можно ли к нему подключиться через LDAP
Практический план: начать с Варианта А (ручная admin-панель — 3 дня разработки). Это сработает для пилота и даже для 200–300 человек, если изменения происходят редко. Если станет ясно что AD есть и IT готов дать доступ — добавить Вариант Б позже, это не переделка, а расширение.
1
Admin-панель: создание, редактирование, блокировка пользователей
Страница /admin/users: список всех пользователей, кнопки «Добавить», «Изменить роль», «Заблокировать». JWT-токен содержит роль — при каждом запросе сервер проверяет права. Роли: Директор НПО / Рег. менеджер / Менеджер качества / Оператор.
JWT + ролиPostgreSQL RLS3–4 дня разработки
2
Row-Level Security в PostgreSQL: данные изолированы на уровне БД
RLS — это защита на уровне базы данных. Региональный менеджер не может увидеть данные другого НПО даже если в коде будет ошибка — БД просто не вернёт лишние строки. Это второй рубеж защиты после JWT.
PostgreSQL RLSКритическая безопасность

Фоновый процесс раз в час (после ETL) проверяет пороги: выручка <-10%, NPS <4.0, укомплектованность <80%. Алерт = Web Push в браузер + email. Журнал алертов в приложении с кнопкой «Принято к работе».

Риски
Ключевые риски и митигация
Высокий
Описание схемы DWH займёт больше времени, чем ожидалось
Митигация: начать с 5–7 самых нужных таблиц (АЗС-справочник + KPI + NPS), это даёт уже работающий ETL. Остальные таблицы описывать итеративно, когда понадобятся.
Высокий
Нет бюджета на GPU-сервер, а локальный ИИ критически важен
Митигация: для пилота (10–15 человек) использовать CPU-инференс (Qwen2.5-Coder-7B Q2_K, ~5 tok/s, ответ за 15–30 сек). Это медленно, но рабочий прототип. Обосновать закупку GPU через экономию времени АУП.
Средний
DWH-команда не даёт read-only доступ из-за политики безопасности
Митигация: запросить доступ к специально выделенной схеме-витрине, которую DWH-команда сделает для приложения. Это стандартная практика разграничения доступа.
Средний
Качество Text-to-SQL <75% из-за неполного описания схемы
Митигация: кнопка «👎 Неверно» в интерфейсе собирает реальные примеры ошибок → дополнить описание полей → качество растёт итеративно.
Низкий
Один разработчик — риск блокировок на непрофильных задачах
Митигация: строгая последовательность этапов (не начинать следующий, пока не закрыт текущий). Таймбоксы: если задача не решается за 3 дня — искать обходной путь, не застревать.
Открытые вопросы v3.0
Требуют ответа до или в процессе разработки
?
Есть ли в ЛУКОЙЛ Active Directory (AD) — система управления аккаунтами сотрудников?
Если да — роли и пользователи могут синхронизироваться автоматически. Если нет — вполне достаточно ручной admin-панели. Уточнить у IT-отдела.
?
Разрешает ли политика ИБ обработку данных на облачном GPU (Selectel/Яндекс Cloud)?
Если нет — нужна закупка собственного GPU-сервера (~400–500 тыс. ₽). Если да — можно начать с аренды без капитальных затрат. Это влияет на планирование бюджета Этапа 4.
?
Есть ли в DWH поле updated_at / modified_at в ключевых таблицах?
Без этого поля инкрементальный ETL (только изменения за час) невозможен — придётся каждый раз загружать всю таблицу. Проверить при первом подключении к DWH.
?
Кто в компании владеет данными АЗС в DWH и может подтвердить описание?
Для валидации описания схемы нужен человек, который знает что означают поля — аналитик данных, DWH-инженер или бизнес-аналитик. Без этой встречи высок риск неправильного понимания метрик.
