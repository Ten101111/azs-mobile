# Демонстрационный контур ИИ: вопрос → SQL → ответ

Контур показывает, как обращение на русском языке превращается в SQL-запрос
к витрине и возвращает цифры. Всё работает локально: ни корпоративной сети,
ни реквизитов хранилища, ни внешних сервисов не требуется.

## Из чего состоит

| Модуль | Назначение |
|---|---|
| `contract.py` | Описание витрины для модели: две таблицы, формулы производных показателей, правила, шесть примеров «вопрос → SQL» |
| `generator.py` | Обращение к локальной модели через Ollama. Недоверенный генератор: его результат проверяется |
| `validator.py` | Детерминированный валидатор. Разбор в синтаксическое дерево, один SELECT, каталог таблиц и колонок, системная подстановка области данных, лимит строк |
| `scope.py` | Построение области данных по роли: ОНПО, РУ, ТМ, объект |
| `executor.py` | Выполнение на соединении только для чтения, с ограничением по времени |
| `journal.py` | Журнал обращений: и успешных, и отклонённых |
| `pipeline.py` | Порядок шагов и одна попытка перегенерации при отказе валидатора |
| `api.py` | Эндпоинты `/api/ai/status`, `/api/ai/ask`, `/api/ai/journal` |
| `build_reference.py` | Сборка справочника объектов из `data/stations.json` |
| `demo.py` | Прогон демонстрационного сценария из командной строки |
| `selfcheck.py` | Самопроверка контура: библиотеки, данные, валидатор, изоляция области данных, модель, живая генерация |

## Что показывает демонстрация

Главное здесь — не модель, а валидатор. Область данных подставляется системно
и не снимается ни формулировкой вопроса, ни текстом сгенерированного запроса:
таблица подменяется подзапросом с фильтром, поэтому ограничение действует всюду,
где таблица встречается, включая соединения и вложенные запросы.

Контрольный пример: один и тот же вопрос «сколько объектов в августе» под
администратором возвращает 2 222, под территориальным менеджером — 17.

## Запуск

```bash
# 1. Модель — берётся уже установленная локально
ollama serve &
ollama list                         # посмотреть, какие модели уже загружены

# 2. Окружение Python 3.11-3.13 (под 3.14 нет сборок pandas и psycopg2)
python3.12 -m venv .venv && source .venv/bin/activate
pip install -r backend/requirements.txt

# 3. Справочник объектов (один раз, и после обновления stations.json)
python3 backend/ai/build_reference.py

# 4. Самопроверка: данные, валидатор, изоляция области, модель, живая генерация
python3 -m backend.ai.selfcheck

# 5. Прогон демонстрационного сценария
python3 -m backend.ai.demo

# 6. Приложение
AI_DEMO_ENABLED=1 uvicorn backend.main:app --reload --port 8000
npm run dev
```

Раздел появится в «Аналитике» отдельной вкладкой «ИИ-аналитик». Он виден только
администраторам и только при включённом `AI_DEMO_ENABLED`.

## Настройки

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `AI_DEMO_ENABLED` | выключено | Включает раздел. Без неё эндпоинты отвечают 404 |
| `AI_MODEL` | `qwen3:8b` | Модель по умолчанию. В интерфейсе выбирается из установленных |
| `AI_MODEL_THINK` | выключено | Рассуждающим моделям (Qwen3) режим размышления для генерации SQL не нужен и по умолчанию выключен |
| `AI_OLLAMA_HOST` | `http://127.0.0.1:11434` | Адрес Ollama |
| `AI_MODEL_TIMEOUT` | `120` | Предел ожидания модели, с |
| `AI_SQL_TIMEOUT` | `15` | Предел выполнения запроса, с |
| `AI_DB_BACKEND` | `sqlite` | Исполнитель запросов: `sqlite` — стенд, `postgres` — витрина в ОХД |
| `AI_SQL_DIALECT` | `sqlite` | Диалект разбора в валидаторе; для витрины — `postgres` |
| `AI_SQL_SCHEMA` | не задана | Схема витрины, если таблицы адресуются с префиксом |
| `DWH_DB_HOST`, `DWH_DB_PORT`, `DWH_DB_NAME`, `DWH_DB_USER`, `DWH_DB_PASSWORD` | — | Реквизиты витрины при `AI_DB_BACKEND=postgres`. На публичном сервере не размещаются |
| `AI_KPI_DB` | `data/kpi_metrics.sqlite3` | База показателей стенда, открывается только на чтение |
| `AI_REFERENCE_DB` | `data/ai_reference.sqlite3` | Справочник объектов |
| `AI_JOURNAL_DB` | `data/ai_journal.sqlite3` | Журнал обращений |

## Модель

Движок — любая модель, установленная в Ollama. Имя задаётся переменной `AI_MODEL`,
а в интерфейсе выбирается из списка загруженных: `/api/ai/status` отдаёт то, что
вернула `ollama list`. Смена модели не затрагивает ни контракт витрины, ни
валидатор, ни область данных — меняется только генератор.

Для рассуждающих моделей семейства Qwen3 учтены две особенности. Во-первых, они
печатают ход рассуждения в блоке `<think>…</think>` — он вырезается из ответа до
разбора SQL, в том числе когда закрывающего тега нет из-за обрыва генерации.
Во-вторых, при генерации SQL размышление только удлиняет ответ, поэтому по
умолчанию оно выключено: запрос уходит с `think: false`, а к тексту вопроса
добавляется директива `/no_think`. Включить обратно — `AI_MODEL_THINK=1`.

## Где находятся данные

Целевая схема проекта: **DWH → витрина данных → ИИ**. Модель никогда не работает
с сырыми таблицами хранилища: в них сотни объектов, нет деловой семантики и есть
данные, которые за пределы контура не выходят. ИИ обращается только к витрине —
согласованному слою с понятными показателями. Это и есть «витрина как контракт»
из бизнес-требований.

Исполнитель запросов вынесен за отдельный интерфейс, и у него две реализации:

| `AI_DB_BACKEND` | Источник | Когда применяется |
|---|---|---|
| `sqlite` | Локальная база агрегатов `data/kpi_metrics.sqlite3` | Демонстрационный стенд |
| `postgres` | Витрина данных в ОХД, соединение `READ ONLY` с ограничением времени на стороне сервера | Целевой контур |

Переход на витрину — смена трёх переменных (`AI_DB_BACKEND`, `AI_SQL_DIALECT`,
реквизиты `DWH_DB_*`) и переописание каталога таблиц и колонок в `validator.py`
и `contract.py` под её состав. Валидатор, подстановка области данных, журнал,
эндпоинты и интерфейс остаются прежними.

Ограничение, заданное самим проектом: публичный сервер не подключается к
корпоративной сети и не хранит реквизитов хранилища. Поэтому в целевой схеме
исполнитель с реквизитами витрины работает внутри защищённого контура вместе с
моделью, а приложение обращается к нему по API и получает только агрегаты.

## Границы демонстрации

1. Источник данных стенда — локальная база агрегатов, а не витрина. Структура
   контура при этом совпадает с целевой: ИИ читает согласованный слой, а не
   сырые таблицы хранилища.
2. Переключатель роли в интерфейсе — способ показать область данных, а не
   ролевая модель продукта. Настоящая модель ролей описана в бизнес-требованиях
   и опирается на учётные записи, а не на выбор из списка.
3. `revenue` — выручка с налогами, топливо и НТУ вместе. Это не показатель
   «выручка без НДС» из согласованной витрины: демонстрационная база собрана
   из более раннего выгрузочного запроса.
4. Конверсия считается как доля чеков с НТУ в общем числе чеков. В методике
   знаменателем служат топливные чеки — отдельного счётчика в этой базе нет.
5. Уровень сервиса, планы и оценки в демонстрационной базе отсутствуют:
   вопросы о них ответа не дадут.
6. Классификация вопросов по матрице «роль × класс» здесь не выполняется —
   это следующий шаг, описанный в приложении к бизнес-требованиям.
