## Этап 0: Инфраструктура (1–2 недели)

**Цель:** одна командой `docker-compose up` поднимает всё окружение.

### Задачи

**1. Docker Compose**
- Контейнеры: Nginx + FastAPI + PostgreSQL (app) + Redis + Ollama (позже)
- Файлы `.env` для local / staging / production
- Все секреты — только через переменные окружения

**2. Миграция SQLite → PostgreSQL + PgBouncer**
- 1 000 пользователей = 1 000 потенциальных соединений с БД
- PostgreSQL без пулера не выдержит
- PgBouncer держит 20–50 реальных соединений и «раздаёт» их всем
- Инструмент миграции схемы: Alembic

**3. Redis**
- Хранение сессий пользователей (быстро, не нагружает БД)
- Кеш тяжёлых агрегатов с TTL 30 минут
- При часовом обновлении DWH — оптимальный баланс свежести и нагрузки
- Снижает нагрузку на DWH в 10–20 раз

**4. Read-only подключение к DWH**
- Запросить у DWH-команды пользователя с правами только SELECT
- Зафиксировать: список схем, к которым есть доступ
- Это вход в Этап 1

## Этап 1: Описание архитектуры данных DWH с нуля (3–5 недель)

**Это самый важный этап.** Без описания данных:
- ETL пишется вслепую (не знаем что тянуть)
- Text-to-SQL ИИ выдаёт мусор (модель не знает структуру)
- Каждая ошибка позже стоит в 5× дороже

### Пошаговый процесс

#### Шаг 1: Автовыгрузка структуры (1–2 дня)

```python
import psycopg2, yaml

conn = psycopg2.connect("host=dwh-host dbname=dwh user=ro_user password=...")
cur  = conn.cursor()

cur.execute("""
  SELECT t.table_schema, t.table_name, c.column_name,
         c.data_type, c.is_nullable,
         col_description(
           (t.table_schema||'.'||t.table_name)::regclass::oid,
           c.ordinal_position
         ) AS comment
  FROM information_schema.tables t
  JOIN information_schema.columns c USING (table_schema, table_name)
  WHERE t.table_schema NOT IN ('information_schema','pg_catalog','pg_toast')
  ORDER BY t.table_schema, t.table_name, c.ordinal_position
""")

schema = {}
for schema_n, table_n, col, dtype, nullable, comment in cur.fetchall():
    key = f"{schema_n}.{table_n}"
    if key not in schema:
        schema[key] = {"description": "TODO", "columns": {}}
    schema[key]["columns"][col] = {
        "type": dtype, "nullable": nullable == "YES",
        "description": comment or "TODO"
    }

with open("dwh_schema_draft.yaml", "w", encoding="utf-8") as f:
    yaml.dump(schema, f, allow_unicode=True, default_flow_style=False)
```

Результат: YAML-черновик со всеми таблицами и колонками, поля `description` = TODO.

#### Шаг 2: Разведочный анализ (EDA) по каждой таблице (3–5 дней)

Для каждой нужной таблицы выполнить:

-- Образцы данных

-- Кардинальность ключевых полей
SELECT status_code, COUNT(*) FROM schema.table_name GROUP BY 1 ORDER BY 2 DESC;

## Этап 2: ETL — синхронизация DWH → App каждый час (2–3 недели)

**Расписание:** APScheduler запускает ETL в :15 каждого часа (через 15 минут после обновления DWH).
Данные в приложении отстают максимум на 1 час 15 минут.

### Задачи

**1. Инкрементальный ETL**
```python
# Забираем только изменения — намного быстрее полной загрузки
WHERE updated_at > (SELECT last_run FROM etl_log WHERE table_name = 'kpi_hourly')
```
- Ночью — полная перезагрузка (раз в сутки, в 02:00)
- Вставка: `INSERT … ON CONFLICT DO UPDATE` (upsert)

**2. Materialized Views для дашбордов**
```sql
-- Создать один раз, обновлять после каждого ETL
CREATE MATERIALIZED VIEW mv_station_daily_kpi AS
SELECT station_id, date_trunc('day', kpi_timestamp) as day,
       SUM(revenue) as revenue_total, AVG(nps) as nps_avg
FROM kpi_hourly GROUP BY 1, 2;

-- Обновление без блокировки чтения
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_station_daily_kpi;
```

**3. Мониторинг свежести данных**
```sql
CREATE TABLE etl_log (
    id SERIAL PRIMARY KEY,
    table_name VARCHAR NOT NULL,
    started_at TIMESTAMP NOT NULL,
    finished_at TIMESTAMP,
    rows_loaded INTEGER,
    error TEXT
);
```
- Эндпоинт `GET /api/data-health` — статус последнего ETL
- На фронте: плашка «Данные актуальны на: 47 минут назад»
- Алерт на email если ETL не запускался более 2 часов

**4. Первый реальный пилот**
После первого успешного ETL — пригласить 10–15 пилотных пользователей.
Собрать обратную связь: верные ли данные, понятен ли интерфейс.
Это критически важно до разработки RBAC.

## Этап 3: RBAC + Управление пользователями + Алерты (3–4 недели)

### Управление пользователями: что это и как реализовать

**Проблема:** при 1 000 пользователях нужно организовать:
- Кто создаёт аккаунты новым сотрудникам
- Кто назначает роли (директор vs. оператор)
- Кто блокирует доступ при увольнении

**Вариант А — Ручная admin-панель (рекомендуется на старте)**
- Страница `/admin/users`: список + кнопки «Добавить», «Изменить роль», «Заблокировать»
- Администратор (вы или назначенный IT-сотрудник) управляет вручную
- Разработка: 3–4 дня
- Подходит для пилота и до ~200 пользователей

**Вариант Б — Active Directory / LDAP (для 1 000 пользователей)**
- Active Directory — корпоративная IT-система, где уже есть все сотрудники ЛУКОЙЛ
- Новый сотрудник в AD → аккаунт создаётся автоматически
- Уволился, IT отключил в AD → доступ в приложении закрыт автоматически
- Роль из группы AD: «АЗС_Директора» → роль «Директор НПО»
- **Уточнить у IT:** есть ли AD в компании и можно ли подключиться через LDAP

### Роли (RBAC)

| Роль | Видит данные |
|------|-------------|
| Директор НПО | Все АЗС своего НПО |
| Региональный менеджер | АЗС своего региона |
| Менеджер по качеству | Все АЗС (только чтение) |
| Оператор АЗС | Только своя АЗС |

**Реализация безопасности (два рубежа):**
1. JWT-токен с ролью — сервер проверяет при каждом запросе
2. PostgreSQL Row-Level Security (RLS) — БД не вернёт лишние строки даже при ошибке в коде

### Задачи этапа

- Admin-панель: создание/редактирование/блокировка пользователей
- JWT с ролями + PostgreSQL RLS
- Push-алерты по KPI-порогам (Web Push API + VAPID + email)
  - Пример порогов: выручка < -10%, NPS < 4.0, укомплектованность < 80%
  - Журнал алертов с кнопкой «Принято к работе»
- Экспорт Excel (openpyxl) и PDF (WeasyPrint) в корпоративном стиле

## Этап 4: Локальный ИИ Text-to-SQL (6–8 недель)

**ВАЖНО:** Только локальные модели. Данные компании не должны покидать инфраструктуру. Никаких запросов к OpenAI, Anthropic, Yandex GPT и другим внешним API.

### Архитектура

```
Пользователь: «Какие 5 АЗС дали наибольшую выручку за прошлый месяц?»
    ↓
POST /ai/query
    ↓
Ollama (localhost:11434)
Модель: Qwen2.5-Coder-14B-Instruct Q4_K_M
System prompt: [YAML-схема из Этапа 1 — 30–100 страниц описания данных]
    ↓
SQL: SELECT station_id, SUM(revenue) FROM kpi_hourly
     WHERE kpi_timestamp >= date_trunc('month', NOW() - INTERVAL '1 month')
     GROUP BY 1 ORDER BY 2 DESC LIMIT 5
    ↓
Проверка безопасности (sqlparse — только SELECT, никаких DROP/INSERT/UPDATE)
Таймаут 5 секунд
    ↓
Выполнение через read-only connection
    ↓
Результат таблицей + возможность «Скачать Excel»
```

### Модель

| Параметр | Значение |
|---------|---------|
| Модель | Qwen2.5-Coder-14B-Instruct Q4_K_M |
| VRAM | 10–12 GB (RTX 4090 — с запасом) |
| Скорость | 15–25 токенов/сек на RTX 4090 |
| Время ответа | < 5 сек на SQL-запрос |
| Параллельных запросов | 1–2 (остальные в очереди через Redis) |

### Задачи

- Развернуть Ollama: `docker run -d --gpus all -p 11434:11434 ollama/ollama`
- Загрузить модель: `ollama pull qwen2.5-coder:14b`
- Сервис `/ai/query` с проверкой SQL и очередью (Redis Queue)
- Чат-интерфейс: история диалога, результат таблицей, экспорт в Excel
- Кнопки «👍 Верно» / «👎 Неверно» — сбор датасета для улучшения качества

**Связь с Этапом 1:** качество YAML-описания схемы напрямую определяет качество ИИ. Чем точнее описаны поля — тем точнее SQL.

## Риски

| Риск | Уровень | Митигация |
|------|---------|----------|
| Описание DWH займёт дольше плана | Высокий | Начать с 5–7 нужных таблиц, остальные итеративно |
| Нет бюджета на GPU-сервер | Высокий | Пилот на CPU-инференс, GPU обосновать через экономию времени АУП |
| DWH-команда не даёт read-only доступ | Средний | Запросить доступ к витрине данных (staging schema) |
| Качество Text-to-SQL < 75% | Средний | Улучшать промпт итеративно по сигналам «👎 Неверно» |
| Один разработчик — риск блокировок | Низкий | Строгая последовательность этапов, таймбоксы по 3 дня |
