# Состояние проекта

## 1. Коротко

«Классификатор АЗС» — внутренняя мобильная PWA-платформа для поиска и просмотра АЗС, их атрибутов, карты, KPI, кадровых рекомендаций и аналитики. Ближайшая цель — стабилизировать существующий web-контур и данные; затем формализовать DWH и запустить изолированный локальный AI-аналитик. AI-аналитик пока не реализован.

## 2. Границы и продуктовая ценность

Пользователи MVP: руководители/региональные управляющие, территориальные менеджеры и аналитики центрального офиса. Базовые сценарии: найти АЗС, открыть карточку и карту, увидеть атрибуты и качество данных, выбрать месяц KPI, сравнить объекты и посмотреть рекомендации по персоналу.

Целевой сценарий AI: ответить на аналитический вопрос по данным DWH, показать период, покрытие и основания ответа. Модель не должна иметь прямого или неограниченного доступа к DWH.

## 4. Фактическая архитектура

```text
Пользователь → Nginx → React/PWA
                      ↘ FastAPI → SQLite auth
                                 → SQLite KPI
                                 → локальные JSON АЗС / персонал

Корпоративный компьютер + VPN → DWH PostgreSQL → SQL-выгрузка → HTTPS импорт KPI
```

Принцип безопасности: публичный web-сервер не должен устанавливать VPN в корпоративную сеть и не должен хранить DWH-реквизиты. Для текущей KPI-витрины на сервер передаются только агрегаты, а не сырые транзакции.

## 5. Данные и ключевые правила

- Основной ключ АЗС: `КССС_union` / `ksss`; он связывает источники.
- Первичный реестр берётся из Excel-листа `cls_AZS`. Реальные выгрузки и `stations.json` приватны и не должны коммититься.
- В исходных данных известны проблемы: нулевые/некорректные координаты, пропуски, неоднородные справочники и статусы. UI должен показывать предупреждения качества, но не маскировать факты.
- KPI рассчитаны на уровне «АЗС × день»; для неполного месяца MoM/YoY сравниваются за одинаковое число дней.
- При отсутствии реальных данных пользователь должен видеть «нет информации», а не синтетические значения.

## 6. Заявленное состояние, требующее проверки перед использованием как факта

ТЗ v4 фиксирует контрольный снимок на 11.07.2026: 2 139 616 дневных агрегированных строк, 31 месяц, диапазон 01.01.2024–10.07.2026 и 2 479 уникальных КССС в KPI-витрине. Это документный снимок, а не текущее измерение. Перед любым решением по производительности его нужно снять заново из production.

## 7. Ограничения текущего контура

- Текущий VPS мал: 1 vCPU, около 957 MiB RAM, без GPU. Он подходит для сайта/небольшого пилота, но не для локальной LLM.
- Текущий backend — модульный монолит; микросервисы пока не нужны.
- Корпоративный доступ к DWH зависит от VPN/MobilePass+. Постоянный автоматический доступ не подтверждён.
- Доступ по корпоративной почте не равен RBAC: ограничений по строкам/организационной структуре пока нет.
- Рабочее дерево уже содержит незакоммиченные изменения. Перед интеграцией или деплоем их нужно отдельно просмотреть; эта база их не перезаписывает.
